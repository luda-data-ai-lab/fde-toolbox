## 1. 개요

### 1.1 목적

FDE(Forward Deployed Engineer)가 고객사 현장에 들어가 **진단 → 분석 → 설계 → 구축 → 운영**까지 수행하는 전 과정을 하나의 도구로 지원한다. 지금까지 개별 앱으로 기획했던 CoachQ(현 DiscoveryQ), BusinessFlowDesk, 인터페이스 관리, ExMigrate, DevTracker를 하나의 툴박스로 통합하고, 신규 모듈인 OntoMap(온톨로지), SpecForge(설계 문서 생성), AgentHub(AI 에이전트 관리)를 추가한다.

개별 앱과의 차이는 **모듈 간 데이터가 이어진다는 것**이다. 현장 인터뷰에서 나온 인사이트가 업무 흐름도로, 흐름도의 시스템이 인터페이스 목록으로, 흩어진 용어와 데이터 구조가 하나의 온톨로지로, 분석 결과가 개발 명세로, 명세가 개발 작업과 AI 에이전트로 이어지며 전 과정이 하나의 고객사 프로젝트 안에서 추적된다.

### 1.2 대상 사용자

| 사용자 | 설명 |
|---|---|
| LUDA 관리자 | 툴박스 운영, 고객사 생성, LUDA 자산(템플릿·질문 뱅크 등) 관리 |
| FDE | 고객사 현장에서 진단·분석·설계·구축·운영 업무를 수행 |
| 고객사 관리자 | 자사 데이터 열람, 산출물 승인, 연동 어댑터 활성화 승인 |
| 고객사 사용자 | 자사 데이터 열람, 인터뷰 워크시트·흐름도 등 검토 |

### 1.3 핵심 설계 원칙

1. **오프라인 완결**: 외부 연동 없이 모든 기능이 동작한다. 입력은 수동 입력과 파일 가져오기, 출력은 파일 내보내기로 완결된다.
2. **멀티 테넌트 데이터 모델, 단독 설치 우선 배포**: 모든 고객 데이터는 고객사(Tenant) 단위로 격리된다. 기본 배포는 고객사별 단독 설치이며, 같은 코드로 LUDA 호스팅 방식도 지원한다.
3. **LUDA 자산과 고객 데이터의 분리**: 여러 고객사에 재사용되는 노하우(질문 뱅크, 흐름 템플릿, 상위 온톨로지, 명세 템플릿, 에이전트 템플릿, 규칙팩)와 고객사 고유 데이터를 스키마 수준에서 분리한다.
4. **선택형 연동**: 외부 연동(LLM, 에이전트 런타임, Git 등)은 어댑터로 분리하며, 기본은 전부 꺼져 있고 고객사별로 승인 후 켤 수 있다. 연동이 꺼져 있어도 기능은 대체 경로로 동작한다.
5. **시도 단계의 최소 범위**: 각 모듈은 MVP 수준으로 시작하고, 확장은 사용 후 결정한다.

## 2. 용어 정의

| 용어 | 정의 |
|---|---|
| Tenant (고객사) | 데이터 격리의 최상위 단위. 하나의 고객 기업 |
| Engagement (과제) | 고객사 안에서 수행하는 FDE 과제 단위. 예: "NeoSlon MES AI 전환 1차" |
| LUDA 자산 (Asset) | 고객사와 무관하게 재사용되는 템플릿·지식. 고객 데이터를 포함하지 않음 |
| 시스템 레지스트리 | 고객사의 IT 시스템(MES, ERP, LIMS 등) 목록. 모든 모듈이 공유 |
| 어댑터 (Adapter) | 외부 시스템과의 연동을 담당하는 선택형 구성 요소 |
| 규칙팩 (Rule Pack) | AI 코딩 에이전트에게 전달하는 작업 규칙 묶음. Devin.md 등에 자동 첨부 |
| 승격 (Promote) | 고객사에서 개선된 산출물을 고객 데이터를 제거한 뒤 LUDA 자산으로 반영하는 절차 |
| 온톨로지 | 고객사 업무의 개념(엔티티), 속성, 관계와 그것이 실제 시스템 데이터 어디에 있는지를 정의한 의미 모델 |
| 상위 온톨로지 | 업종 공통 개념 모델(예: 제조 공통). LUDA 자산이며 고객사 온톨로지가 이를 상속·확장 |
| 용어 사전 | 표준 용어와 정의, 부서별 호칭·약어를 묶은 목록. 온톨로지의 출발점 |

## 3. 역할과 권한

| 기능 | LUDA 관리자 | FDE | 고객사 관리자 | 고객사 사용자 |
|---|---|---|---|---|
| 고객사 생성·삭제 | O | - | - | - |
| LUDA 자산 편집 | O | 제안 | - | - |
| 과제 생성·편집 | O | O (배정된 고객사) | - | - |
| 모듈 데이터 작성·편집 | O | O (배정된 고객사) | 일부 (코멘트) | - |
| 모듈 데이터 열람 | O | O (배정된 고객사) | O (자사) | O (자사) |
| 산출물 승인 | - | 요청 | O | - |
| 연동 어댑터 활성화 | 설정 | 요청 | 승인 | - |
| 감사 로그 열람 | O | 자사 과제 | O (자사) | - |
| 고객사 데이터 내보내기 | O | O | O (자사) | - |

FDE는 배정된 고객사의 데이터에만 접근할 수 있다. 한 FDE가 여러 고객사에 배정될 수 있으며, 화면 상단에서 현재 작업 고객사를 전환한다.

## 4. 전체 구조

### 4.1 단계와 모듈

| 단계 | 모듈 | 역할 |
|---|---|---|
| 진단 | DiscoveryQ | 현장 인터뷰·코칭 질문과 세션 기록 |
| 진단 | FlowDesk | As-Is / To-Be 업무 흐름도 작성 |
| 분석 | I/F 관리 | 시스템 간 인터페이스 목록과 연결 현황 |
| 분석 | ExMigrate | 고객사 엑셀 자산의 구조·수식 분석 |
| 분석 | OntoMap | 용어 사전·개념 모델·데이터 매핑 (온톨로지) |
| 설계 | SpecForge | Spec.md / Devin.md 생성 |
| 구축 | DevTracker | 개발 프로젝트·작업·프롬프트 추적 |
| 운영 | AgentHub | AI 에이전트 템플릿·배포·평가 관리 |

모든 모듈은 **공통 코어** 위에서 동작하고, 외부 연동은 **어댑터 계층**을 통해서만 이루어진다.

### 4.2 모듈 간 데이터 흐름

```
DiscoveryQ 인사이트 ──▶ FlowDesk 흐름도 생성의 입력
FlowDesk 노드 ──▶ 시스템 레지스트리의 시스템 참조
I/F 관리 ◀──▶ 시스템 레지스트리 (시스템·연동 관계의 원천)
ExMigrate 분석 결과 ──▶ SpecForge 입력
DiscoveryQ 용어·ExMigrate ERD·I/F 데이터 설명·FlowDesk 문서 노드 ──▶ OntoMap 후보
OntoMap 개념 ──▶ 시스템 레지스트리·ERD·I/F로 매핑
OntoMap 용어 사전·개념 모델 ──▶ SpecForge 입력
OntoMap 고객사 개념 ◀── AgentHub 인스턴스의 개념 바인딩
DiscoveryQ·FlowDesk·I/F·ExMigrate 산출물 ──▶ SpecForge ──▶ Spec.md / Devin.md
SpecForge 문서 ──▶ DevTracker 프로젝트 생성
DevTracker 프로젝트 ──▶ AgentHub 에이전트 템플릿·인스턴스와 연결
AgentHub 운영 이슈 ──▶ DevTracker 이슈 ──▶ 다음 버전 개발
```

모듈 간 연결은 모두 **내부 참조**(ID 링크)로 구현하며, 사용자가 "다음 단계로 보내기" 버튼으로 명시적으로 넘긴다. 자동 동기화는 하지 않는다.

## 5. 공통 코어

### 5.1 고객사·과제 관리
- 고객사 생성·수정·보관(archive)·삭제. 삭제 시 해당 고객사의 모든 데이터와 첨부파일을 영구 삭제하며, 삭제 전 전체 내보내기를 권고한다.
- 과제 생성·수정. 과제는 상태(준비/진행/보류/완료), 기간, 담당 FDE, 설명을 가진다.
- 대부분의 모듈 데이터는 과제에 소속된다. 시스템 레지스트리처럼 고객사 전체에 걸친 데이터는 고객사에 직접 소속된다.

### 5.2 사용자·인증
- 로컬 계정(이메일 + 비밀번호). 외부 SSO는 범위 외(향후 어댑터).
- 사용자는 역할과 소속(LUDA 또는 특정 고객사), 배정 고객사 목록을 가진다.
- 최초 설치 시 LUDA 관리자 계정을 생성하는 초기화 절차를 제공한다.

### 5.3 시스템 레지스트리
- 고객사의 IT 시스템 목록: 이름, 약칭, 유형(MES/ERP/LIMS/WMS/SCADA/그룹웨어/기타), 담당 부서, 운영 형태(온프레미스/클라우드), DB 종류, 비고.
- I/F 관리, FlowDesk, AgentHub가 공통으로 참조한다. 기존 인터페이스 관리 기획의 "시스템 정보"를 코어로 승격한 것이다.

### 5.4 LUDA 자산 라이브러리
- 자산 종류: 질문 뱅크, 흐름 템플릿, I/F 엑셀 템플릿, 상위 온톨로지, 용어 사전 엑셀 템플릿, 명세 템플릿, 규칙팩, 에이전트 템플릿.
- 자산은 버전을 가지며, 고객사 데이터에서 자산을 참조할 때는 특정 버전을 참조한다.
- 자산 편집은 LUDA 관리자만 가능하며, FDE는 개선 제안(승격 요청)을 할 수 있다.
- 단독 설치 환경 간 자산 이동을 위해 자산 패키지 가져오기·내보내기(JSON)를 지원한다.

### 5.5 승격(Promote) 절차
1. FDE가 고객사 산출물(예: 개선된 에이전트 프롬프트, 흐름도)에 대해 승격 요청을 생성한다.
2. 시스템이 원본을 복제한 승격 초안을 만들고, 고객사명·시스템명·사람 이름 등 고객 식별 정보로 의심되는 부분을 표시한다.
3. FDE가 식별 정보를 제거·일반화했음을 체크리스트로 확인한다.
4. LUDA 관리자가 검토 후 자산의 새 버전으로 반영한다.
5. 승격 이력(원본 고객사 ID는 감사 로그에만 기록)을 남긴다.

### 5.6 감사 로그
- 기록 대상: 로그인, 데이터 생성·수정·삭제, 내보내기, 승인, 어댑터 활성화·비활성화, 외부 호출(어댑터 사용 시), 승격.
- 감사 로그는 수정·삭제할 수 없다(고객사 삭제 시에만 함께 삭제).
- 고객사 관리자는 자사 로그를 열람하고 CSV로 내보낼 수 있다.

### 5.7 가져오기·내보내기
- 모든 모듈은 자신의 데이터를 파일로 내보낼 수 있다(모듈별 형식은 6장).
- 고객사 전체 내보내기: 고객사의 모든 데이터와 첨부파일을 하나의 ZIP(JSON + 원본 파일)으로 내보낸다. 같은 버전의 툴박스에 다시 가져올 수 있어야 한다.
- 모든 JSON 내보내기 형식은 `schema_version` 필드를 가진다.

### 5.8 첨부파일
- 로컬 파일 저장소에 고객사별 디렉터리로 분리 저장한다.
- 업로드 크기 제한과 허용 확장자는 설정으로 관리한다.

### 5.9 홈 대시보드
- FDE: 배정된 고객사·과제 목록, 최근 작업, 열린 액션 아이템, 중단 메모가 있는 작업.
- 고객사 관리자: 자사 과제 현황, 승인 대기 산출물.
- LUDA 관리자: 전체 고객사 현황, 승격 요청 대기 목록.

## 6. 모듈 명세

### 6.1 DiscoveryQ — 현장 인터뷰·코칭

**목적**: 고객사 이해관계자 인터뷰와 FDE/멘티 코칭 세션에서 질문을 고르고, 답변·인사이트·액션 아이템을 기록한다. LLM 없이 질문 뱅크 기반으로 동작한다.

**주요 기능**
- 질문 뱅크(LUDA 자산): 8개 카테고리(현황 파악, 기술 역량 진단, 문제 해결, 목표 설정, 성장/회고, 프로세스/협업, 온보딩, 커리어 개발). 질문마다 카테고리, 태그, 대상(경영진/현업/IT/개발자), 후속 질문을 가진다.
- 세션 유형: 현장 인터뷰 / 코칭. 유형에 따라 기본 추천 카테고리가 달라진다.
- 대상자 관리: 과제별 인터뷰 대상자(이름, 부서, 직무, 담당 시스템). 코칭 유형에서는 멘티로 사용.
- 세션 워크시트: 질문 선택 → 세션 진행 중 답변 기록 → 인사이트 태깅 → 액션 아이템 생성(담당자, 기한, 상태).
- 인사이트를 FlowDesk로 보내기: 선택한 인사이트를 FlowDesk 흐름도 생성 입력으로 전달.
- 과제별 질문 세트 커스터마이징: 자산 질문을 복제해 고객사 전용 질문으로 수정 가능(고객 데이터로 저장).

- 자동 보고서(Word .docx, 서버에서 오프라인 생성): 세션 보고서(질문·답변, 인사이트·태그, 액션 아이템, 세션에서 등록한 용어와 부서별 호칭)와 인게이지먼트 진단 보고서(개요·주요 태그·세션 목록·전체 액션 아이템·등록 용어·세션별 기록).

**내보내기**: 세션 워크시트 Markdown/Word/PDF(PDF는 Phase 3), 인게이지먼트 진단 보고서 Word, 액션 아이템 CSV.

### 6.2 FlowDesk — 업무 흐름도

**목적**: 고객사 업무 흐름(As-Is / To-Be)을 편집 가능한 캔버스로 작성한다.

**주요 기능**
- 인터랙티브 캔버스: 노드(업무 단계, 의사결정, 시스템, 문서, 담당 역할), 엣지, 스윔레인(부서/역할), 메모.
- 시스템 노드는 시스템 레지스트리의 시스템을 참조한다. 레지스트리에 없는 시스템은 바로 추가할 수 있다.
- 관점 선택: 현업 / PM / 개발자 / 경영진 / 컨설턴트. 생성 시 강조할 정보와 상세 수준이 달라진다.
- 생성 방식 세 가지:
  1. **수동 작성**: 빈 캔버스 또는 흐름 템플릿(LUDA 자산, 예: "도료 제조 주문→출하", "품질 검사") 에서 시작.
  2. **프롬프트 복사 모드**(LLM 어댑터 꺼짐): 사용자가 입력한 설명과 DiscoveryQ 인사이트로 LLM용 프롬프트를 조립해 보여주고, 사용자가 외부 LLM에서 받은 결과 JSON을 붙여넣으면 캔버스로 변환한다.
  3. **자동 생성**(LLM 어댑터 켜짐): 같은 프롬프트로 LLM 어댑터를 호출해 바로 캔버스를 생성한다.
- As-Is와 To-Be 흐름도를 짝으로 관리하고 나란히 비교한다.
- 버전 스냅샷: 수동 저장 시점마다 스냅샷을 남기고 되돌릴 수 있다.

**내보내기**: JSON(재가져오기 가능), PNG, SVG, Mermaid.

### 6.3 I/F 관리 — 인터페이스 관리

**목적**: 고객사 시스템 간 인터페이스를 목록화하고 연결 현황을 시각화한다.

**주요 기능**
- I/F 목록: I/F ID, 이름, 송신 시스템, 수신 시스템, 연동 유형(DB Link, API, 파일, MQ, EAI, 기타), 주기(실시간/배치 주기), 데이터 설명, 담당자, 상태(운영/개발/폐기), 비고.
- 엑셀 템플릿(LUDA 자산) 다운로드 → 작성 → 업로드. 업로드 시 검증 결과(오류 행, 미등록 시스템)를 보여주고 미등록 시스템을 레지스트리에 추가할지 선택하게 한다. 템플릿 시트는 "인터페이스 리스트"와 "시스템 연동정보" 두 개.
- 대시보드: 시스템별 I/F 수, 연동 유형별 분포, 상태별 현황.
- 연결 현황 그래프: 시스템을 노드, I/F를 엣지로 하는 네트워크 그래프. 시스템 클릭 시 관련 I/F 목록.

**내보내기**: 엑셀(템플릿과 동일 형식), CSV, 그래프 PNG.

### 6.4 ExMigrate — 엑셀 자산 분석

**목적**: 고객사가 엑셀로 관리하는 업무 데이터의 구조와 수식을 분석해 DB 이관 설계의 근거를 만든다. 툴박스에서는 **분석과 스크립트 생성까지**만 수행하며 외부 DB에 직접 적재하지 않는다.

**주요 기능**
- 엑셀 업로드(.xlsx, .xlsm은 매크로 실행 없이 읽기만).
- 구조 분석: 시트 목록, 헤더 행 추정, 컬럼별 추정 타입·null 비율·고유값 수, 병합 셀·빈 행 등 품질 경고.
- 수식 분석(단계적): 1단계 수식 존재 여부와 위치, 2단계 단순 함수(SUM, IF, VLOOKUP 등) 사용 빈도와 시트 간 참조, 3단계 복잡 수식 해석은 범위 외(향후).
- ERD 초안: 시트를 테이블 후보로, 참조 관계를 관계 후보로 제시. 사용자가 확정·수정.
- 스크립트 생성: 확정된 ERD로 DDL(SQLite/PostgreSQL/MSSQL)과 데이터 적재 스크립트(Python)를 생성해 내려받기.

**내보내기**: 분석 리포트 Markdown, ERD Mermaid, DDL/적재 스크립트 ZIP.

### 6.5 OntoMap — 온톨로지 (신규)

**목적**: 고객사 업무의 개념, 속성, 관계를 하나의 의미 모델로 정리하고, 각 개념이 실제로 어느 시스템·테이블·컬럼·인터페이스에 있는지 매핑한다. 부서마다 다른 용어를 통일하고, 개발 명세와 AI 에이전트가 같은 개념 체계를 쓰게 하는 것이 목표다. OWL 추론이나 SPARQL 질의 같은 학술적 기능이 아니라 **실무형 경량 온톨로지**로 한정한다.

**구성 요소**
- **용어 사전**: 표준 용어, 정의, 동의어·부서별 호칭(부서 태그 포함), 약어, 출처(인터뷰 세션, 엑셀 컬럼, I/F 등), 상태(후보/확정/폐기), 연결된 개념.
- **개념 모델**
  - 개념: 이름, 정의, 상위 개념(상위 온톨로지 개념 또는 같은 고객사 개념), 식별 속성, 담당 부서.
  - 속성: 이름, 데이터 타입, 단위, 필수 여부, 허용값·규격(예: 점도 범위).
  - 관계: 이름, 대상 개념, 카디널리티(1:1/1:N/N:M), 역관계 이름.
- **데이터 매핑**: 개념 → 시스템(레지스트리) + 테이블/엔티티, 속성 → 컬럼, 관계 → 외래키 또는 I/F. 매핑 출처(수동/ExMigrate/I/F)를 기록한다. 개념별 매핑 커버리지(매핑된 시스템 수, 미매핑 속성)를 보여준다.
- **상위 온톨로지 (LUDA 자산)**: 업종 공통 개념 모델. 초기 자산으로 "제조 공통"을 제공한다. 고객사 개념은 상위 개념을 상속·확장하며, 상위 온톨로지의 특정 버전을 참조한다.

**후보 추출과 확정**
- 규칙 기반 후보 추출(LLM 불필요): ExMigrate 확정 ERD의 테이블·컬럼 → 개념·속성 후보, I/F 데이터 설명과 FlowDesk 문서·데이터 노드 → 개념 후보, DiscoveryQ 세션에서 "용어로 등록"한 표현 → 용어 후보.
- 후보 목록에서 FDE가 확정, 기존 항목과 병합, 무시를 선택한다. 이름 유사도가 높은 기존 용어·개념을 병합 후보로 함께 보여준다.
- LLM 어댑터가 켜져 있으면 인터뷰 기록에서 용어 후보 추출, 개념 간 관계 제안, 정의 초안 작성을 지원하고, 꺼져 있으면 프롬프트 복사 모드로 동작한다. LLM 결과도 반드시 후보 목록을 거쳐 FDE가 확정한다.

**검증**: 순환 상속, 상위 개념이 없는 고아 개념, 정의 없는 확정 용어, 매핑 없는 확정 개념, 같은 이름의 중복 개념을 경고로 보여준다.

**시각화**: 개념 그래프(개념=노드, 관계=엣지, 상속=점선). 상위 개념·시스템·부서로 필터링하고, 개념 클릭 시 속성·매핑·관련 용어를 보여준다.

**승격**: 고객사 개념 중 업종 공통으로 쓸 만한 것을 승격 절차(5.5)로 상위 온톨로지의 새 버전에 반영한다.

**가져오기**: 용어 사전 엑셀 템플릿(LUDA 자산), 툴박스 JSON.

**내보내기**: 용어 사전 엑셀/CSV, OWL(Turtle), JSON-LD, Mermaid 클래스 다이어그램, 온톨로지 문서 Markdown.

### 6.6 SpecForge — 설계 문서 생성 (신규)

**목적**: 과제 산출물을 모아 AI 코딩 에이전트(Devin 등)에게 전달할 Spec.md와 Devin.md를 만든다.

**주요 기능**
- 문서 템플릿(LUDA 자산): Spec 템플릿, Devin 템플릿. 섹션 구조와 각 섹션을 채우는 규칙을 가진다.
- 입력 선택: 과제의 DiscoveryQ 인사이트, FlowDesk 흐름도, I/F 목록, ExMigrate 분석 결과, OntoMap 용어 사전·개념 모델, 자유 입력 요구사항 중 선택.
- 온톨로지 반영: OntoMap을 입력으로 선택하면 Spec.md에 "용어 사전"과 "도메인 개념 모델" 섹션을, Devin.md에 "데이터 모델은 이 개념·용어를 따른다"는 지시와 개념-테이블 매핑표를 자동 삽입한다.
- 조립: 선택한 입력을 템플릿 섹션에 매핑해 초안을 만든다(LLM 없이 규칙 기반).
- 규칙팩 첨부: 선택한 규칙팩(LUDA 자산)을 Devin.md의 "작업 규칙" 섹션에 자동 삽입.
- 보강: LLM 어댑터가 켜져 있으면 초안을 LLM으로 다듬고, 꺼져 있으면 프롬프트 복사 모드로 동작.
- 편집기: Markdown 편집·미리보기, 버전 저장, 버전 간 비교(diff).
- DevTracker로 보내기: 확정 문서로 DevTracker 프로젝트를 생성하고 문서를 첨부.

**내보내기**: Spec.md, Devin.md 개별 또는 ZIP.

**기본 규칙팩(초기 자산)**
- 완료는 실행 증거(테스트 결과, 실행 로그, 스크린샷)로만 선언한다.
- 작업은 작게 나누고 작업 단위로 커밋·PR 한다.
- 명세에 없는 기능이나 외부 호출을 추가하지 않는다.
- 여러 대안을 비교할 때 합의점·차이점·전제·판단 근거를 분리해 보고한다.
- 사용자가 해결책을 먼저 제시해도 문제 정의를 먼저 확인한다.

### 6.7 DevTracker — 개발 추적

**목적**: 과제에서 파생된 개발 프로젝트의 작업, 프롬프트, 문서, 이슈를 추적한다.

**주요 기능**
- 프로젝트: 과제 소속. 설명, 상태, 기술 스택, 저장소 링크, 실행 환경 메모, 배포 정보(수동).
- 작업(Task): 제목, 설명, 상태(대기/진행/검토/완료/보류), 우선순위, 담당, 기한. **중단·재개 메모**(멈춘 지점, 다음에 할 일)를 가진다.
- 프롬프트 기록: 작업에 연결된 프롬프트와 결과 요약, 사용 도구(Devin/Claude Code 등), 일시. 작업 단위로 개발 흐름을 추적.
- 문서: Markdown 문서 첨부·편집(SpecForge 문서 포함).
- 이슈: 버그/개선/질문. AgentHub 운영 기록에서 이슈를 생성할 수 있다.
- 테스트 기록: 일시, 범위, 결과, 증거 첨부.
- 비용 기록(수동): 도구 사용료, 토큰 비용 등.
- 칸반 보드와 목록 보기, 프로젝트 대시보드(작업 진행률, 열린 이슈, 최근 프롬프트).

**내보내기**: 프로젝트 전체 Markdown 리포트, 작업·이슈 CSV.

### 6.8 AgentHub — AI 에이전트 관리 (신규)

**목적**: FDE 활동으로 만들어진 AI 에이전트를 템플릿(LUDA 자산)과 배포 인스턴스(고객 데이터)로 나눠 관리한다. **에이전트를 실행하지 않는 관리 계층**이다.

**에이전트 템플릿 (LUDA 자산)**
- 이름, 목적, 적용 업종·업무, 입력/출력 설명.
- 시스템 프롬프트, 사용 도구·MCP 명세(텍스트), 권장 모델, 가드레일 정책(금지 행동, 사람 승인이 필요한 행동, 데이터 접근 범위).
- 다루는 개념: 에이전트가 읽고 쓰는 데이터를 상위 온톨로지 개념으로 선언한다(예: 로트, 품질검사, 작업지시).
- 버전: 버전마다 변경 사유와 이전 버전과의 프롬프트 diff.
- 평가 세트: 테스트 케이스(입력, 기대 결과, 판정 기준).
- 버전별 평가 결과: 케이스별 통과/실패, 메모, 증거 첨부. 수동 입력 또는 CSV 가져오기.

**배포 인스턴스 (고객 데이터)**
- 템플릿 버전 참조, 고객사·과제, 배포 형태(단독 설치/호스팅/고객사 자체 환경), 연결 시스템(시스템 레지스트리 참조), 설정 오버라이드(프롬프트 추가 지시 등), 상태(준비/시범/운영/중지), 담당 FDE, 관련 DevTracker 프로젝트.
- 개념 바인딩: 템플릿이 선언한 상위 개념을 이 고객사 온톨로지의 개념과 연결한다. 연결된 개념의 데이터 매핑을 통해 에이전트가 실제로 접근할 시스템·테이블을 확인할 수 있고, 바인딩되지 않은 개념이 있으면 배포 상태를 "운영"으로 바꿀 때 경고한다.
- 운영 기록: 기간별 실행 건수, 성공/실패, 장애 내용, 비용, 사용자 피드백. 수동 입력 또는 CSV 가져오기.
- 운영 기록에서 DevTracker 이슈 생성.
- 인스턴스 개선 사항을 승격 절차로 템플릿 새 버전에 반영.

**대시보드**: 템플릿별 배포 고객사 수, 인스턴스 상태 현황, 버전별 평가 통과율.

**내보내기**: 템플릿 패키지 JSON, 인스턴스 설정 JSON, 운영 리포트 Markdown.

## 7. 연동 어댑터

### 7.1 원칙
- 외부로 나가는 모든 통신은 어댑터 안에서만 발생한다. 어댑터 밖의 코드는 네트워크 호출을 하지 않는다.
- 모든 어댑터는 기본 비활성이다.
- 어댑터를 사용하는 기능은 비활성 상태의 대체 경로를 반드시 가진다.

### 7.2 어댑터 목록

| 어댑터 | 용도 | 시도 단계 범위 |
|---|---|---|
| LLM | FlowDesk 자동 생성, SpecForge 보강, OntoMap 용어·관계 제안 | **구현** (Anthropic Claude API) |
| 에이전트 런타임 | AgentHub 운영 기록 자동 수집 (luda-mcpserver 등) | 인터페이스 정의만 |
| Git | DevTracker 커밋·PR 정보 조회 | 인터페이스 정의만 |

### 7.3 활성화 절차
1. FDE 또는 LUDA 관리자가 고객사 설정에서 어댑터 활성화를 요청한다.
2. 화면에 **데이터 반출 범위**를 표시한다: 어떤 기능에서, 어떤 데이터가, 어느 외부 주소로 전송되는지.
3. 고객사 관리자가 승인한다(단독 설치에서 고객사 관리자가 없으면 LUDA 관리자가 승인하고 사유를 기록).
4. 인증 정보(API 키 등)를 고객사별로 암호화 저장한다.
5. 활성화·비활성화, 모든 외부 호출(일시, 기능, 사용자, 전송 데이터 크기, 결과)을 감사 로그에 남긴다.

전역 설정으로 "모든 어댑터 사용 불가" 모드를 제공한다. 이 모드에서는 어댑터 활성화 메뉴 자체가 보이지 않는다.

## 9. 비기능 요구사항

- **보안**: 비밀번호 해시(argon2), 세션 토큰은 httpOnly 쿠키, 어댑터 인증 정보 암호화 저장, 업로드 파일 확장자·크기 검증, 엑셀 매크로 미실행.
- **격리 검증**: 고객사 간 데이터 누출 여부를 자동 테스트로 상시 검증한다.
- **오프라인**: 외부 CDN, 외부 폰트, 원격 분석 스크립트를 사용하지 않는다. 모든 정적 자원은 번들에 포함한다.
- **언어**: UI 기본 한국어. 문자열은 다국어 구조(i18n)로 관리해 영어를 추가할 수 있게 한다.
- **백업**: 단독 설치에서 DB와 첨부파일을 하나의 백업 파일로 만드는 명령 제공.
- **성능 목표**: 고객사당 I/F 1,000건, 흐름도 노드 300개, 온톨로지 개념 500개·용어 3,000개, 엑셀 파일 20MB 수준에서 원활히 동작.
- **유지보수성**: 모듈별 디렉터리 분리, 모듈 간 참조는 공통 코어의 ID 링크로만.

## 12. 성공 기준

- 실제 고객사 과제 1건을 툴박스만으로 진단부터 에이전트 배포 기록까지 수행할 수 있다.
- 외부 연동을 모두 끈 상태에서도 모든 모듈의 핵심 기능이 동작한다.
- 한 고객사 데이터가 다른 고객사 화면·API·내보내기에 나타나지 않음이 자동 테스트로 보장된다.
- 한 과제에서 만든 질문 세트·흐름 템플릿·에이전트 템플릿이 다른 고객사 과제에서 재사용된다.
- 에이전트 템플릿을 새 고객사에 배포할 때 개념 바인딩으로 데이터 위치를 확인할 수 있어, 매핑 작업이 처음부터 다시 시작되지 않는다.
